# Security and privacy

Mailficient has no telemetry. Message bodies and credentials are not logged. Remote resources are blocked at the parsed-HTML allowlist, Content Security Policy, and WebKit request-policy layers by default; users can explicitly allow remote images for one message, a trusted sender, or all senders. Full HTML formatting can also preserve a message's embedded style rules, classes, IDs, and inline styles. Scripts and privileged WebKit APIs remain disabled in both modes. HTML is sanitized before rendering and external links open through the system handler only after showing their real destination. Attachments are decoded into a private application directory with normalized filenames and size limits; saving requires an explicit destination and never opens the file automatically.

Outgoing attachment imports use private copies and delete incomplete copies after failure or cancellation. Compose delivery cancels unfinished imports, validates To/Cc/Bcc again at the outbound boundary, and locks all draft mutation paths until the send attempt completes, avoiding invalid, mixed, or duplicated MIME submissions.

After the complete draft and its Outbox record are committed, but before SMTP owns the delivery attempt, Mailficient reopens every attachment without following symlinks. Each path must remain a direct child of private draft storage, each object must remain a regular file, and its current size must equal the stored metadata. The 25 MB per-file and 100 MB aggregate MIME-preparation limits are enforced both at this boundary and again inside the Camel MIME builder. A failure remains an ordinary retryable Outbox error and can never be mistaken for an uncertain SMTP result.

Received MIME parts are decoded through an enforcing bounded output stream, not merely trusted size metadata. A single automatically cached attachment is limited to 50 MB and successful cached attachments from one message are limited to 100 MB in total. A part that lies about its decoded size is stopped before it can exceed the boundary, its private staging file is removed, and its sanitized metadata and MIME-part index remain available. If the user explicitly chooses a destination, Mailficient reconnects to the account, refetches that exact part, writes through a private sibling staging file with a 2 GB hard boundary, and atomically moves the completed download into place. Partial downloads are removed and never opened automatically.

Forwarding an uncached attachment uses the same stable server identity and bounded retrieval path with the stricter 25 MB outgoing-attachment limit. The download first lands in a private, randomly named temporary file, is imported into durable private draft storage, and is removed in every completion path. Compose never sends from the temporary file.

Draft discard is database-first: Mailficient removes the durable draft transactionally before cleaning its attachment files. If the database step fails, every attachment remains available when the draft is reopened. File cleanup accepts only direct children of Mailficient's private draft-attachment directory, so corrupt metadata cannot turn discard or post-send cleanup into deletion of an arbitrary user file.

In-app previews are allowlisted to passive image formats, PDF, and bounded UTF-8 text. The declared MIME type, safe extension, detected local type, and file signature must agree before rendering. HTML, SVG, executables, binary data disguised as text, unknown types, non-regular files, and untrusted attachment URIs are not previewed. PDF previews run in a locked-down WebKit view with scripts, storage, WebGL, permissions, and navigation disabled.

Loading remote images for one message does not persist permission. Choosing “Always Load Images” stores only the normalized sender address in the local cache. Preferences → Safety shows compact sender-list summaries that open a separate searchable Sender Lists window for review and immediate revocation; sender trust never enables scripts, privileged APIs, unsafe URL schemes, or unrestricted navigation.

Safe Senders are a revocable local address preference. They permit remote images from that exact address and hide its automatic inline sender-warning card. A separate image-only trust list remains available when the user wants remote content without broader sender preference. Mailficient still calculates receiving-server SPF, DKIM, and DMARC findings, punycode warnings, and misleading-link findings for Safe Senders and keeps them in **Security Details**; link confirmation, attachment checks, and WebKit restrictions are never bypassed. Original headers are rendered as plain selectable text and truncated on a valid UTF-8 boundary at 64 KiB before persistence and display.

Mailing-list unsubscribe is deny-by-default. Only bounded, control-free HTTPS and `mailto:` values from `List-Unsubscribe` are exposed. An advertised one-click endpoint is not submitted automatically: the user sees the destination and confirms before the browser opens. Mailto targets create an editable draft; the decoded address must be valid and the subject is control-free and length-bounded. `http:`, `javascript:`, malformed, duplicate, and oversized targets are discarded.

**Report Phishing** uses the existing durable provider Junk/NotJunk flag and folder-move path and adds the sender to the local block list. The confirmation explicitly says that this is not a provider-specific abuse-report API. It also removes an accidental Safe Sender entry before classification.

Password credentials are stored only through `LibsecretCredentialStore`. Gmail and Microsoft OAuth tokens are requested on demand from GNOME Online Accounts over D-Bus, used in memory for Camel XOAUTH2 authentication, and never persisted by Mailficient. The Camel session rejects unrecognized certificate trust instead of automatically accepting it. TLS certificate errors must be surfaced and never silently bypassed.

Account removal commits the local deletion together with a credential-cleanup journal entry before contacting Secret Service. Keyring cleanup then runs asynchronously and is retried on later launches if the service is temporarily unavailable. This prevents a partial database failure from leaving a configured account whose password was already destroyed, while ensuring stale secrets are not silently forgotten.

Camel certificate prompts never create a trust exception or offer an insecure bypass. Mailficient records the validation reason for the active connection attempt, rejects the certificate, and converts Camel's subsequent generic connection failure into a TLS-specific warning. Account Setup identifies the affected host and explains whether the certificate is untrusted, mismatched, not yet valid, expired, revoked, or cryptographically insecure.

The HTML view disables JavaScript, JavaScript markup, local storage, HTML databases, offline cache, page cache, and WebGL, and denies permission requests. Mailficient parses untrusted HTML with libxml2 in non-networked mode and serializes only an allowlist of passive mail elements and attributes; active elements, inline event handlers, unsafe URL schemes, SVG data images, and remote image sources are discarded. Full HTML formatting additionally retains embedded CSS and selector attributes, but does not relax the active-content rules. The generated document carries a restrictive Content Security Policy that denies scripts, objects, frames, forms, connections, media, and base-URL changes. A message-specific action can reload sanitized HTML with HTTP(S) image URLs retained for that view only.

Startup cache maintenance is constrained to Mailficient's private attachment directories. Referenced draft and received-message files are preserved, missing records are reconciled, and unreferenced files elsewhere on the system are never considered for deletion.

OpenPGP and S/MIME protect the MIME body after attachments and rich alternatives are assembled. OpenPGP keeps GnuPG trust enforcement enabled and automatic network key discovery disabled. Encryption recipients are normalized and deduplicated, include Bcc without writing it into mail headers, and include the sender so a Sent copy remains decryptable. S/MIME delegates key and certificate validation to Evolution Data Server's NSS-backed context. A cryptographic failure occurs before SMTP submission and leaves the durable Outbox draft editable; it is never classified as uncertain delivery.

Incoming cryptographic failures do not relax rendering policy. Successfully decrypted HTML still passes through the same sanitizer, remote-content policy, and locked-down WebKit view as ordinary mail. Signature and decryption descriptions are stored as display metadata, while private keys and certificate passwords are never stored in the mail database.
