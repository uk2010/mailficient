# Architecture

`RemoteContentPolicy` is the security boundary for persistent per-sender image trust. Reading and preferences widgets request policy operations without manipulating its SQLite representation, and the HTML/WebKit layers continue enforcing their independent restrictions after a sender is trusted.

Presentation in `src/ui` depends on the `MailRepository` interface, never on protocols or persistence. `src/models` contains domain data. `src/mail` owns demo and cached repository implementations. `src/services` owns Camel integration, synchronization, sending, threading, search, attachments, notifications, and online-account authorization; `src/security` owns credentials, parsed HTML sanitization, WebKit content policy, and filename policy. Application startup performs dependency wiring.

Startup cache failures are handled by a dedicated `StartupErrorWindow`, not by terminating after a log message. It presents a normal-language recovery action and expandable diagnostics, preserves the database untouched, and lets the application discard partially wired dependencies before retrying initialization. No automatic reset or destructive corruption recovery occurs.

`LocalDataMigration` publishes a legacy Personal Mail directory only after a complete private staging copy and transactional SQLite path rewrite. Draft and received-attachment paths rooted beneath the old directory are rebased to the final Mailficient directory; resource URIs and unrelated paths are untouched. Any copy or rewrite failure recursively removes only the random staging directory and leaves the authoritative legacy data unchanged.

Received attachment responsibilities are split deliberately: `ReceivedAttachmentStore` enforces automatic private-cache limits while parsing MIME, `CacheDatabase` persists remote part indices, `ReceivedAttachmentService` resolves a cached message to its account and server folder, and `CamelMailEngine` performs the user-authorized refetch and atomic destination write. The same service prepares durable private draft copies for forwarding. Reading-pane and compose code contain no Camel objects, credentials, or protocol logic.

`AccountProvisioningService` is the transaction boundary for adding and editing accounts. It validates a replacement through Camel under a temporary account identity and temporary libsecret entries before disconnecting a working session. Only a successful candidate may replace the live credentials and connection. If the final database write or connection fails, the service disconnects the replacement, restores the prior credentials, and reconnects the prior settings. Temporary secrets use the durable credential-cleanup journal, so a Secret Service interruption cannot orphan them silently. Account dialogs collect and display input but do not coordinate credentials, Camel sessions, persistence, or rollback. `AccountStore` keeps that persistence boundary independently testable.

The demo repository is an in-memory implementation of the same production boundary and is enabled only by visual-QA/test startup flags. Normal startup with no account exposes an empty repository and account onboarding, never sample messages. `CamelMailEngine` initializes Camel and its provider registry once, configures Camel IMAPX and SMTP services, performs connection, recursive folder discovery and lifecycle operations, MIME extraction, synchronization, state changes, moves, sending, and Sent filing asynchronously with cancellables, and obtains credentials through replaceable credential and online-account interfaces. `GnomeOnlineAccountService` isolates D-Bus discovery and short-lived OAuth token requests; Camel consumes the tokens through XOAUTH2 without storing them. Failed connection tests remove partially registered Camel services so corrected settings can be retried cleanly. Camel, GIO, and TLS failures are normalized at this boundary into stable application error categories before reaching the interface. `AccountSyncService` coordinates refreshes, queued mutations, reconnects, and new-message detection without putting protocol work in widgets. Both full synchronization and per-account mutation drains are serialized, preventing timer/manual refresh overlap and rapid interface changes from duplicating server work. Real-mail refreshes select cached identities without loading stored bodies, cap each backend session at 250 new MIME messages, release MIME trees after conversion, and commit converted mail in batches of at most 20. When the inventory shows additional uncached mail, the service saves the checkpoint, tears down Camel, and immediately starts another bounded session until caught up; a no-progress guard prevents endless retries on an unparseable message. Text-part decoding has an enforcing 10 MB in-memory boundary. `JunkFilterService` applies normalized address/domain rules only to synchronized Inbox messages; the cache atomically queues Camel Junk/NotJunk flags with the matching folder move so offline classification is recoverable. `FolderService` validates folder requests and keeps Camel operations out of the sidebar and dialogs; `MessageSorter` owns deterministic presentation ordering.

`CacheDatabase` owns schema migration, WAL configuration, offline mail, threading headers, attachment metadata, recoverable draft persistence, the durable Outbox, and queued message mutations/transfers. Server snapshots are installed transactionally, then any still-pending read, flag, or move operations are reapplied before commit so a stale refresh cannot visibly undo offline work. Unread totals remain based on the server's authoritative mailbox counts and are adjusted only by pending local deltas; they are never replaced by the smaller downloaded-message window. `CachedMailRepository` adapts saved drafts and `OutboxItem` records into the same mailbox and message-list boundary as received mail; activating one passes the stored `Draft` back to `ComposeWindow`, including its private attachment copies. Outbox rows expose waiting/failed state without leaking raw protocol errors into the primary interface. Account removal is a single local database transaction covering cached messages, search rows, drafts, Outbox entries, and pending operations. Compose and account-interface code never write SQL. `LibsecretCredentialStore` is the only password implementation and stores secrets using account/protocol attributes; settings and SQLite never contain passwords.

`ComposeWindow` freezes editing, closing, keyboard-send activation, attachment imports, and pending autosaves while delivery owns the draft. This prevents duplicate SMTP submissions and prevents a late autosave from recreating a draft after successful delivery. Cancelled or failed attachment imports remove their incomplete private copy.

`DraftLifecycleService` owns discard ordering outside the compose widget. It commits removal of the durable draft and Outbox records before deleting private attachment copies, so a database failure leaves a completely reopenable draft rather than a row pointing at files that were already destroyed. Cleanup failures after commit leave only a private orphan for bounded cache maintenance. `AttachmentService` refuses to delete paths outside its exact private draft directory, including paths loaded from corrupted metadata.

Outbox delivery state is treated as a safety boundary rather than presentation metadata. Saving the complete draft (including attachment records) and creating its Outbox record occur in one SQLite transaction; a failed Outbox insert rolls the draft change back instead of leaving ambiguous partial state. A queued failure remains retryable, a send whose SMTP response was lost requires an explicit duplicate-delivery warning before the user may send it again, and an already accepted item awaiting local cleanup is read-only and cannot re-enter SMTP. `OutboxStatusView` presents these states and keeps protocol diagnostics behind an expandable technical-details control. `OutboxItem` owns the corresponding resend policy so storage and interface behavior are covered by the same tested state model.

`OutboundService` performs attachment preflight only after the durable Outbox transaction and before account connection or SMTP ownership. `AttachmentService` verifies private path containment, regular-file type, immutable recorded size, and aggregate limits. `CamelMailEngine` independently enforces the declared aggregate limit before reading file contents, bounding in-memory MIME construction even when called through another integration boundary.

Message security is also applied only after the complete bounded MIME body has been constructed. Drafts persist the chosen protocol, signing/encryption flags, and optional identity. `CamelMailEngine` wraps that body with `CamelGpgContext` or `CamelSMIMEContext`, signs before encryption when both are selected, and encrypts for deduplicated To/Cc/Bcc plus the sender. On receipt it unwraps at most the supported encrypt/sign layers, records a concise validity result with the cached message, and leaves a failed decryption local to that message instead of failing the synchronization batch.

Provider throttle responses form a separate `MailError.RATE_LIMITED` path. Camel identifies explicit rate-limit and deferral responses at the protocol boundary; OutboundService records those as retryable failures with exponential backoff. It does not use that path for ambiguous transport loss, which remains in the duplicate-safe uncertain state.

Camel also preserves the SMTP response boundary: when a failed send leaves the transport connected, the provider returned a definitive protocol response; a permanent 5xx response becomes `MailError.SEND_REJECTED`, while other explicit failures become `MailError.SEND_FAILED`. When the transport disappeared before a final response, the result remains an ambiguous connection failure. MIME preparation failures are typed before transport submission. `OutboundService` queues temporary proven failures, parks permanent rejection for user correction, and requires explicit resend confirmation only for timeout, cancellation, offline loss, or dropped transport after SMTP ownership.

Mailbox unread totals and optimistic message state are committed together in one SQLite transaction before the corresponding Camel mutation is queued. The repository emits a single change after commit, so both the sidebar badge and message row refresh from the same state. Demo smart mailboxes calculate their unread totals from their actual messages instead of fixed sample metadata.

`MailSyncResult` carries successful folder data, per-folder issues, and an optional terminal account error across the Camel boundary. A folder whose UID inventory failed has no authoritative inventory in that result, so `CacheDatabase` deliberately skips pruning its cached messages while still installing successful folders transactionally. `AccountSyncService` emits its normal refresh signal after commit and then a friendly partial-failure signal with technical details. Connection-wide authentication, TLS, offline, timeout, and throttle failures stop the remaining folder loop to avoid repeated doomed requests without discarding earlier successes.

The Flatpak build runs both the dependency-free core suite and a Camel boundary suite inside the SDK after installation. The Camel suite requires no personal credentials or external server and verifies initialization, clean recovery from repeated failed account connections, error classification, Bcc privacy, threading headers, and byte-exact binary MIME attachments.

`MailSettingsStore` is the typed preference boundary over the SQLite preferences table. It validates the background-check interval and emits scoped changes so the application can replace its GLib timer without duplicating synchronization or reconnect handlers. `SignatureService` owns signature insertion and identity switching so compose widgets do not implement signature rules. `CacheMaintenanceService` reconciles missing attachment records and removes only unreferenced regular files or symlinks directly inside Mailficient's two private attachment directories; it never scans or deletes user-selected export locations.

`RecipientCompletionService` ranks validated, deduplicated correspondents from the local message cache and excludes the active sending identity. A focused `RecipientCompletionController` binds that replaceable service to each compose entry, owning only popup and keyboard behavior. Recipient parsing and safe insertion remain in the mail layer, including quoted display names containing commas.

Cached messages retain both their formatted display date and the original Unix receive or send timestamp. Search date filters use numeric local-calendar-day boundaries, including daylight-saving transitions. Mailbox filters join the cached mailbox catalog so users can search by the visible or server folder name without knowing an opaque internal identifier.
